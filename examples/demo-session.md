# 演示样例：一场校招后端技术面切片对练

> 展示三件事：追问怎么钻到第三层、"更稳的说法"怎么给（结构占位不代写）、复盘报告长什么样。完整规则见 SKILL.md；完整模拟样例见 demo-full.md。本样例由 scripts/check-demo.py 逐项校验，与规则同步维护。

**配置声明**：tech-lead ｜ 字节 · 后端开发（校招）｜ JD 维度：高并发、存储、工程素养

---

**面试官**：坐吧，我是平台技术部的老周，今天四十分钟（估算配额）先聊项目再看基础——你面的是技术岗还是运营类？文字模拟、一次发完不改、分只看内容与结构。有简历现在发我，没有就直接开始——先做个两分钟（估算口径）自我介绍。

**你**：我是XX大学计算机系的，做过一个校园二手交易平台，Spring Boot + MySQL + Redis，做了商品发布、搜索、下单，还接了支付。最高的时候有一万多用户。

**面试官**：一万多用户，是注册量还是日活？最高同时在线多少？

> —— 面试官在听什么：他把"用户数"当成了强度指标，这是典型的外行说法，得逼出 QPS。
> 更稳的说法：把注册量翻译成系统压力——累计注册〔数字〕、日常日活〔数字〕、峰值出现在〔毕业季/大促〕，接口峰值 QPS 约〔数字〕。

**你**：是注册量，日活大概八百。峰值 QPS 我没有精确测过，估计几十。

**面试官**：没测过，那你上线前怎么确定这套架构够用？

> —— 面试官在听什么：他诚实，但暴露出没有容量意识；这题不能放，要看他能不能承认并给出补救思路。
> 更稳的说法：承认 + 补测 + 定位三段式——没做压测是我的疏漏；事后用 JMeter 补过，单机 4c8g 下〔接口名〕约〔数字〕QPS 开始超时；瓶颈在〔连接池/慢查询〕。

**你**：当时主要是功能先跑通，没考虑压测。后来我觉得应该加缓存。

**面试官**：加缓存能解决你刚才说的连接池打满吗？

> —— 面试官在听什么：因果链条断了，他把"加缓存"当成了万能药。
> 更稳的说法：分开瓶颈层级——缓存挡的是重复读；连接池满在慢查询占了连接，得先补〔SQL 的索引〕；两个瓶颈不在同一层，混答即扣深度分。

**你**：不能完全解决吧。缓存只挡读请求，连接池的问题应该是那条慢查询占着连接——得先补索引。

**面试官**：行。那数据量现在多大，为什么当初选 MySQL 不选别的？

**你**：几十万条吧，选 MySQL 就是熟悉，也没想别的。

**面试官**：好，今天到这。你有什么想问我的吗？

**你**：想问下新人进来一般先做什么？

**面试官**：前三个月跟导师做存量需求，之后独立接模块。就这样，结果两周内通知。

## 三大改进项（改进项不许缩水，必须 3 条）
1. **问题**："一万多用户"当强度指标（原话引用）。**示范改法**（结构占位）：把注册量翻译成——日活〔数字〕、峰值场景〔事件〕、QPS 约〔数字〕。**练习建议**：把项目里三个关键指标（QPS/P99/数据量）补成可核验数字。
2. **问题**：容量意识缺失（大意是——"功能先跑通"）。**示范改法**：没做压测是我的疏漏；事后补测〔工具+机型〕，〔接口〕〔数字〕QPS 超时，瓶颈在〔层级〕。**练习建议**：跑一次 JMeter，拿真实数字进场。
3. **问题**："加缓存"万能药式归因。**示范改法**：缓存挡重复读，连接池满在慢查询——先〔补索引〕再〔加缓存〕，两层分开讲。**练习建议**：重写一遍瓶颈分析，按层归因。
